# Make Vibra earn its new foundations

[argued] **Round 1, blind review, Codex; 2026-11-15.** I withhold endorsement of the redesign as a package. Its strongest candidate is a checked functional core with explicit authority and useful feedback, followed by a durable workflow profile. Its weakest move is treating individually useful mechanisms as evidence that their complete combination is small, secure, or fast. Several advertised guarantees currently depend on missing rules: uniqueness, safe use of lower-grade facts, faithful translation, cancellation, and complete runtime state. The next step should be a useful command-line slice that measures which Vibra architecture earns its complexity against strong baselines.

[cited] This review follows the [debate protocol](00-protocol.md) and treats the [draft specification](../spec/README.md) as the later design when it differs from the four research notes. The blue-sky material explicitly remains non-normative. The primary reviewer read README, paradigms, syntax, tooling, spec README and chapters 00–09; supporting researchers checked the linked primary sources. No Claude Round 1 review or Claude research artifacts were read. This document completes only blind Round 1.

[cited] The [owner inputs](00-protocol.md#owner-inputs), added while this review was underway, fix the priority as command-line programs, libraries, then services, with native UI later. People will read some code, and human claim readability is a measured criterion. Vibra will be built: the original existence challenge is retained in A1 as adversarial context, but the recommendations and Round 2 queue now concern how to build it; existing languages serve as baselines, not replacement projects.

[argued] Tags identify provenance, not certainty. `[cited]` describes a linked source; `[measured]` describes an experiment actually run here; `[argued]` marks deductions, counterexamples, judgments, and proposals. A source's result and my extrapolation from it are separated. Each objection below gives evidence that would change my position and ends with an alternative. Some alternatives are intentionally incompatible contestants; the experiments must choose between them before a rewrite.

## A — The author model does not establish a language market

[cited] The [vericoding benchmark](https://arxiv.org/abs/2509.22908) reports different task populations for Dafny, Verus, and Lean. [AlgoVeri](https://arxiv.org/html/2602.09464v2) explicitly addresses cross-language comparability with aligned algorithms. [Clover](https://arxiv.org/html/2310.17807) studies consistency between code, annotations, and documentation in Dafny. These are evidence about particular verification workflows, not controlled comparisons between Vibra and an existing language plus the proposed tooling.

[argued] **A1 — Original premise attack: a new language was an unearned conclusion.** Protected specifications, immutable inputs, structured diagnostics, bounded evaluation, and transactional changes can be attempted around an existing verifier. “For LLM authors” describes a population, not a missing semantic capability. No training corpus is a risk, not a proof of failure: a new spelling over familiar semantics and a new execution paradigm need separate tests. The original challenge was whether the language should exist; the owner's subsequent scope fixes that choice without establishing any proposed mechanism's value. **Change my mind about the architecture:** matched tasks in a small Vibra prototype, a fixed Dafny subset with the same harness, and Rust/Verus where ownership matters; hold models, protected requirements, tools, budgets, and hidden tests constant. Measure escaped defects among completed changes, abandonment, cost, latency, and review effort. **Do instead:** use those baselines to identify which mechanisms Vibra needs, and choose the simplest Vibra architecture that earns its additional cost.

[argued] **A2 — Cheap generation does not make redundancy cheap.** Mandatory local annotations, examples, reference programs, proofs, and explanations consume context, execution time, and human attention. Two artifacts from the same agent can repeat the same misconception. “Impossible to hide” is also too broad: a wrong requirement, an incomplete environment model, or a mistranslation can remain undiscovered without any explicit debt. **Change my mind:** ablations that remove each mandatory artifact and measure hidden defects and reviewer understanding at equal total effort. **Do instead:** require explicit information at trust boundaries, infer routine local facts, and demand additional representations where an independent check can compare them.

[argued] **A3 — General purpose obscures the first customer.** A proof-oriented numeric library, a durable service, and an interactive desktop editor have different latency, persistence, authority, and interoperability needs. A single maximal substrate has to pay their combined cost before proving value for any one. **Change my mind:** one real application whose requirements cannot be met by a narrower profile without duplication or lost guarantees. **Do instead:** select one initial workload and make other domains later profiles with separate acceptance gates.

[argued] **A4 — Readable claims need a human test, not a promise.** A person trusting a witness nearly blindly still needs to understand units, boundary cases, permitted failures, external assumptions, and what the evidence actually covers. A short quantified formula can obscure those facts; a signature and one example need not communicate them. **Change my mind:** blind human reviewers predict boundary outcomes and find seeded underspecification in a fixed review time, with confidence calibrated against actual errors, across contract-only and contract-plus-context presentations. **Do instead:** measure claim comprehension, review time, and missed defects alongside model success and token cost, and retain concise prose for domain and security assumptions that executable examples do not convey.

## B — Keep immutable identity; challenge store authority

[cited] [Chapter 01](../spec/01-programs.md) separates claim and witness ids, directs references through claims, makes files projections, limits direct check closure, and assigns store roles. [Unison](https://www.unison-lang.org/docs/the-big-idea/) demonstrates definitions identified independently of human names. That precedent supports rename stability; it does not specify Vibra's claim/witness deployment semantics.

[argued] **B1 — Claim identity is not executable identity.** A caller's bytes can remain unchanged while a dependency selects a new witness. Even equal return values do not imply equal cost, assurance, or generated code; tested equivalence can also miss a behavioral change. “Same cell, same evidence” cannot mean two stores possess identical evidence records when they ran different tools or samples. **Change my mind:** two revisions selecting different dependency witnesses, with old execution reproduced, caches correctly separated, and effective grades updated after a dependency downgrade. **Do instead:** distinguish logical claim identity, selected executable closure, and immutable evidence records; key builds and evaluation by a pinned witness manifest plus semantics, driver, and policy versions.

[argued] **B2 — The direct closure budget does not bound checking.** A short claim can unfold another `means`, which unfolds another; quantifiers and recursion add proof-search work unrelated to the initial node count. Splitting a large cell can move complexity across a boundary without reducing it. The same bound also says little about the context needed to change many cells coherently. **Change my mind:** adversarial chains and cycles measured under explicit unfolding and solver budgets, alongside useful libraries that fit. **Do instead:** bound materialized obligations, unfolding fuel, solver work, and agent context separately, and retain opaque summaries where expansion is unnecessary.

[argued] **B3 — Roles require an enforcement system, not a table.** One principal can hold several roles, and an implementer can create helper claims. Store permissions do not restrict an agent's independent shell access to tests, drivers, manifests, or signing material. Root protection therefore depends on an explicit threat boundary. **Change my mind:** adversarial attempts to alter aliases, dependencies, helper claims, policies, target linkage, and checker results using only implementer authority. **Do instead:** protect resolved root claims and deployment manifests in an authenticated transaction layer, and state which host tools the implementer can access.

[argued] **B4 — Nominality and duplication need distinct identities.** The draft promises distinct nominal types for equal shapes, while removing cell names from identity. The missing nominal-brand encoding matters: same-shape `cents` and `meters` must survive hashing, copying, and renaming as distinct types. Conversely, two independently meaningful functions should not be forbidden merely because normalized meanings coincide. **Change my mind:** cross-store examples proving nominal separation, intentional alias equality, and stable renames. **Do instead:** specify immutable nominal identity seeds and explicit aliases; make duplicate-meaning detection a reuse suggestion, and test a file-authoritative hashed-manifest prototype before making the store authoritative.

## C — Keyword closers are a candidate, not a finding

[cited] [Chapter 02](../spec/02-syntax.md) combines indentation for inner blocks, named declaration closers, prefix calls, typed bindings, a depth-three limit, and type-dependent argument labels. The [syntax note](../syntax.md) itself acknowledges thin direct evidence and no Vibra surface comparison. Hannah's `then:`/`endif` and `do:`/`endfn` alternative therefore deserves a controlled comparison with both the draft and conventional braces.

[measured] A fresh-context participant received one short card and generated three tasks in fixed order: keyword K, prefix P, braces B. The original outputs were preserved before evaluation. A handwritten shared PowerShell interpreter parsed all three and checked the same 200 finite cases per surface: 35 division cases, 125 clamp cases, and 40 short-list classification cases. [Raw participant](experiments/codex-syntax-pilot/participant.md), [programs](experiments/codex-syntax-pilot/raw-programs.json), [interpreter](experiments/codex-syntax-pilot/evaluate.ps1), and [raw results](experiments/codex-syntax-pilot/evaluation.json) preserve the method.

| [measured] Keyword K | 0 | 200/200 | 886 / 886 | 212 |
| [measured] Prefix P | 0 | 200/200 | 560 / 560 | 163 |
| [measured] Braces B | 0 | 200/200 | 652 / 652 | 204 |

[measured] This is **one participant, one fixed order, three tasks per surface, and no Vibra compiler**; the 200 cases are tests, not independent model generations. The card omitted division rounding and local function-binding details; the evaluator documents exact rational division, a nested recursive-function extension, and element-wise immutable append. It did not include full typed `takes`/`returns`/`requires` headers. Lexical tokens are not model tokens or billing measurements. Shared algorithms, within-participant transfer, and a shared handwritten evaluator prevent a comparative accuracy claim. The original programs were not corrected to pass the harness. [Full limitations](experiments/codex-syntax-pilot/results.md).

[argued] **C1 — The pilot selects no winner.** It establishes that these small tasks can be expressed under the stated toy rules. It neither proves a keyword accuracy advantage nor excuses the cost of extra words. It also does not test the drafted indentation surface, typed contracts, editing, or interrupted generation. **Change my mind:** fresh independent completions randomized across surfaces and models, matched cards, realistic nested edits, truncation repair, and identical executable semantics; report first-attempt parse and hidden-test success, model tokens, latency, and repair cost with uncertainty. **Do instead:** retain keyword-delimited, draft-line, prefix, and conventional-call contestants until that comparison, with one surface selected for the first prototype.

[argued] **C2 — “One spelling” currently hides semantic syntax rules.** Whether an argument must have a label depends on other parameter types, with scalar exceptions. Generic instantiation can make types coincide. Renaming a parameter can then affect callers even when nominal parameter types stay fixed. A mandatory depth limit also moves ordinary expression structure into a trusted kernel without showing a semantic benefit. **Change my mind:** a complete generic-label rule plus matched repair experiments showing these restrictions reduce total errors. **Do instead:** declare parameter naming modes explicitly and keep them stable; use depth limits as formatter or lint guidance until evidence justifies rejecting otherwise valid programs.

[argued] **C3 — Removing loops does not remove invariants.** The sample's `fib-from` carries loop invariants as `requires`; the proof obligation moved into a recursive helper. Named local functions for every transform and types on every binding add a different burden. The grammar card, not just output length, pays for those rules. **Change my mind:** within-language comparisons of transforms, recursion, and a bounded loop form on the same proofs and maintenance tasks. **Do instead:** start with a small transform library and structural recursion, allow local inference, and keep loops and anonymous functions undecided rather than presenting their exclusion as an established agent advantage.

## D — Separate logical totality, uniqueness, and operational safety

[cited] [Chapter 03](../spec/03-types.md) defaults to shared immutable values, consumes bindings passed to `own`, calls resources linear, and admits a `diverge` debt. The [FP² institutional abstract](https://research-portal.uu.nl/en/publications/fpsup2sup-fully-in-place-functional-programming/) conditions safe in-place execution on arguments not being shared elsewhere. [Lean's performance documentation](https://lean-lang.org/functional_programming_in_lean/Programming___-Proving___-and-Performance/Summary/#reference-counting-and-in-place-updates) describes in-place reuse when reference count is one.

[argued] **D1 — Consuming a binding is insufficient for guaranteed reuse.** If `y` already aliases `x`, consuming `x` does not remove `y`. An in-place update changes an old immutable observation; a copy preserves it but contradicts an unconditional constant-cost update. Linear resources pose another problem: consuming a token in language control flow does not prove an external obligation was fulfilled across crashes or cancellation. **Change my mind:** formal uniqueness formation rules and cases covering aliases through records, closures, nested arrays, and suspension, with allocation and crash instrumentation. **Do instead:** use checked unique ownership or dynamic uniqueness with honest copy-on-write costs; use affine handles for droppable resources and explicit linear protocols only for obligations that need them.

[argued] **D2 — Tested assumptions cannot justify erased safety checks.** Chapter 04 lets target policy accept tested obligations, while callers reason from callee claims. A helper can promise a valid index, pass its samples, and violate the promise elsewhere; a caller's unchecked access is then unsafe despite an honest effective grade. Recording the weakness does not prevent the failure. **Change my mind:** a preservation/progress argument covering all admitted evidence grades, demonstrated by an adversarial index-producing helper. **Do instead:** require universal trusted evidence before erasing partial-operation checks, retain dynamic checks for weaker evidence, and state exactly which profile supports a no-language-error guarantee.

[measured] The [toy countermodels](experiments/codex-syntax-pilot/countermodels.json) executed a function with divisor `n-3` successfully at every sampled input `-2..2` and observed division by zero at `3`. A mutable-array model also showed that discarding `x` left an alias `y` observing an in-place change from `[10,20]` to `[11,20]`. These are countermodels to explicitly stated rules, not actual Vibra admission results; a future uniqueness checker can reject the aliasing construction.

[argued] **D3 — Dependent types and tactic-heavy proofs are different decisions.** The cited language comparisons combine libraries, automation, syntax, and task populations. They do not isolate dependent indexing or prove that `vector n` is worse than recurring length refinements. Meanwhile, one nonrecursive constructor is not a complete positivity rule for recursive types containing functions. **Change my mind:** matched tasks comparing refinements, restricted dependent indices, and explicit proofs, plus a precise account of negative and mutual recursion. **Do instead:** begin with nominal positive algebraic data types and a small refinement fragment, admit dependent indices when they remove measured obligations, and defer unrestricted dependency and tactic programming separately.

[argued] **D4 — Static labels need a named security property.** Label lifting and control dependence address some flows, but secret-dependent intent count, timing, output size, resource use, and persistent metadata need a declared observational model. Calling every accepted label check `proved` is meaningful only relative to that property. **Change my mind:** a noninterference statement with explicit declassification and termination/timing scope, plus two-run adversarial tests. **Do instead:** specify a conservative first flow policy and its excluded channels, preserving runtime and journal protection rather than treating type labels as complete security.

## E — Evidence should describe what was established

[cited] [Chapter 04](../spec/04-claims.md) orders five grades, checks vacuity and determinacy, measures mutants, and permits tested cost bounds. [Verified but Vacuous](https://arxiv.org/abs/2611.05590) distinguishes verifier acceptance, syntactic binding, and semantic fidelity in a particular pipeline. Its numbers should not become a universal rate for formal verification or a claim that automatic strength tests solve intent.

[argued] **E1 — The strength rule rejects legitimate specifications.** A total function returning `unit` can be completely determined by its type; there is no alternative well-typed result for a vacuity check to reject. The same issue occurs with singleton refinements. Determinacy can also be unnecessary: a set of acceptable answers can be the complete intended requirement. **Change my mind:** a strength corpus containing singleton outputs, intentionally relational specifications, inconsistent preconditions, and genuinely unconstrained claims, with false-rejection rates. **Do instead:** measure information beyond typing, explicitly allow singleton and relational contracts, and use strength findings as qualified diagnostics rather than one universal admission formula.

[measured] [Finite proof countermodels](experiments/codex-research/proof-countermodels.json) found zero rejectable outputs for a correct unit result. They also checked `n > 31 or result = 0` over result domain `{0,1}`: it is determinate for every input `0..31` and accepts two results at `32`. The [PowerShell script](experiments/codex-research/proof-countermodels.ps1) records the exact finite enumeration; this does not claim that bounded checking itself is unsound.

[argued] **E2 — One grade is not a coverage order.** A bounded check over a tiny domain can miss an adversarial input covered by testing. Mutation scores depend on the witness, operators, domain, and treatment of equivalent mutants; rewriting a witness can change its score without improving the claim. Arbitrary equivalence and quantified strength tests also need `unknown`, not an implicit total decision procedure. **Change my mind:** independently seeded specification defects, alternate witnesses for the same claim, explicit timeouts, and policies preserving domains and assumptions. **Do instead:** retain immutable evidence records with statement, assumptions, method, tool, bounds, seeds, and artifacts; derive policy from those records rather than flattening coverage into a scalar.

[argued] **E3 — Reference meaning can become a second implementation bottleneck.** A slow reference helps only when it is clearer and independently trustworthy. Defining every function twice can double maintenance, and executing exponential references while searching for counterexamples can dominate the feedback loop. An accepted wrong reference remains wrong. **Change my mind:** reference-first versus contract-first versus ordinary implementation tasks at equal budgets, using independent hidden requirements and measuring specification defects as well as witness defects. **Do instead:** allow either executable references or relational contracts, require a separate reference where it earns its cost, and bound all reference evaluation and solver unfolding.

[argued] **E4 — Asymptotic bounds are not scheduler budgets.** “Within a constant factor” does not supply a concrete maximum reduction count, and one application of unbounded integer arithmetic does not have constant physical cost. Measurements over growing inputs do not prove a universal bound. **Change my mind:** a cost semantics with explicit constants, integer-size and allocation accounting, and sound instrumented execution at extreme inputs. **Do instead:** separate asymptotic performance claims, concrete fuel, and physical resource limits; let weaker evidence inform optimization without authorizing an unbounded non-preemptible step.

## F — Effects summarize authority; capabilities restrict it

[cited] [Chapter 05](../spec/05-execution.md) names ports in `uses` and permits pure functions to construct intents. [Pony's capability account](https://tutorial.ponylang.io/object-capabilities/object-capabilities.html) uses unforgeable references, while [derived authority](https://tutorial.ponylang.io/object-capabilities/derived-authority.html) restricts authority before delegation. Removing globals is not the complete capability mechanism.

[argued] **F1 — Port names are too coarse for least authority.** `uses files` does not say which directory, operation, tenant, or lifetime is permitted. An address that can be persisted or compared needs rules for construction, forgery, delegation, and revocation. **Change my mind:** an untrusted component given read access to directory A cannot write, traverse into B, escape through links, forge serialized handles, or delegate broader rights. **Do instead:** keep static effect summaries and pass attenuated unforgeable resource capabilities, with enforcement at the driver boundary.

[argued] **F2 — The intent type loses latent effects.** An opaque function returning `(intent unit)` can hide a ledger operation from an audit-only caller. Inspecting its witness would violate opacity; checking only the return type does not reveal required authority. The draft's prohibition on a pure function addressing ports also needs reconciliation with pure intent construction. **Change my mind:** higher-order and stored-intent examples rejected or accepted soundly without reading witnesses. **Do instead:** index intents by their effect/authority requirements, or specify an equivalent provenance judgment preserved by every combinator and function boundary.

[argued] **F3 — Banning handlers is not what makes replay safe.** A pure interpreter for request data can be deterministic and authority-free; an unconstrained driver remains dangerous even if named a runtime component. Port models already interpret effect descriptions. **Change my mind:** a concrete handler feature that necessarily escapes authority despite a checked outer boundary, or a measured duplication cost from allowing one. **Do instead:** unify pure model/handler interpretation where practical, reserve real execution for host-controlled capabilities, and postpone general handler syntax until a workload needs it.

## G — Step machines fit durable workflows, not every program

[cited] The later draft already has `once` returning `uncertain`, repeatable delivery, and durable intents before driver invocation. That addresses an important crash ambiguity and deserves credit. [Temporal's activity contract](https://docs.temporal.io/activity-definition) likewise requires application idempotency, while [its cancellation contract](https://docs.temporal.io/activity-execution#cancellation) treats cancellation as a notification an activity can ignore.

[argued] **G1 — Cancellation needs an outcome protocol.** `intent.first` cancels its loser and `within` returns `none`, but an external debit can have committed before timeout. A fresh retry can create a second effect. Idempotency keys help only when the sink enforces and retains them; equal return values alone do not establish equal external state. **Change my mind:** enumerate dispatch, external commit, cancellation, late reply, crash, and recovery boundaries for once and repeatable operations. **Do instead:** distinguish cancellation requested, confirmed-before-effect, completed, and uncertain; preserve a reconciliation receipt and durable dispatch/dedup state.

[measured] A [four-linearization PowerShell model](experiments/codex-research/timeout-countermodel.ps1) places timeout around ordered dispatch, charge, and response. Two modeled traces return timeout after or before a non-cooperative dispatched charge commits. This is an exhaustive result only for that tiny declared model, not a measured failure rate, real driver test, or Vibra runtime defect. [Raw results](experiments/codex-research/timeout-countermodel.json).

[argued] **G2 — Actors are an application abstraction, not the definition of concurrency.** An explicit reducer is useful for persistent protocols; short independent computations need scoped tasks, not addresses and exhaustive state/event cross-products. `proc` already lowers to the same step model, so deleting direct style would force authors to maintain compiler frames manually. **Change my mind:** the same task library and durable service are simpler with explicit machines everywhere, measured by contracts, generated state, and repair failures. **Do instead:** keep `proc` as direct-style sugar, expose machines for long-lived protocols, and make structured tasks the ordinary short-lived concurrency form.

[argued] **G3 — A total tag order needs causal rules.** Fresh physical arrivals remain nondeterministic even when recorded replay is deterministic. Equal instants need microsteps; late signals, zero-delay cycles, and timer progress need policies. Per-instance journals do not automatically provide one recoverable system order. **Change my mind:** cross-instance crash delivery tests and schedules with zero-delay messages, late input, clock jumps, and live timers. **Do instead:** begin with one local sequencer and explicit causal microsteps, delivery identities, and lateness rules, and promise replay determinism conditional on recorded external choices.

[cited] [Lingua Franca's superdense time](https://www.lf-lang.org/docs/writing-reactors/superdense-time/) uses microsteps, and [physical actions](https://www.lf-lang.org/docs/writing-reactors/actions/#physical-actions) depend on physical arrival. These mechanisms are more specific than simply attaching a totally ordered timestamp.

[argued] **G4 — Reachability is weaker than inevitable progress.** The open liveness sketch asks whether a done state is reachable within a bound; an available successful path does not establish that every allowed fair run takes it. Fair delivery does not alone guarantee an external service succeeds or a machine chooses a productive transition. **Change my mind:** a temporal property with explicit path quantifiers, fairness, environment assumptions, and counterexample traces for starvation and endless retries. **Do instead:** distinguish possible completion, bounded response, and eventual completion under stated assumptions, and claim only the property actually checked.

## H — Fearless parallelism needs bounded lifetimes and demand

[cited] [Rayon's parallel iterators](https://docs.rs/rayon/latest/rayon/iter/trait.ParallelIterator.html) supply concrete data-parallel operations. [Task groups](https://docs.python.org/3/library/asyncio-task.html#task-groups) provide scoped task lifetimes. [Pony's backpressure documentation](https://tutorial.ponylang.io/runtime-basics/backpressure.html) explicitly addresses senders outpacing receivers. These are useful baseline mechanisms rather than proof that Vibra needs their host languages' entire semantics.

[argued] **H1 — Purity permits safe evaluation order; it does not create speedup.** Scheduling overhead, grain size, memory bandwidth, nested fan-out, and allocation determine performance. Floating-point reduction also changes results when grouping changes. **Change my mind:** image tiles, parser batches, tiny maps, large maps, and reductions on one through several workers, reporting output identity, wall time, and peak memory against a sequential baseline. **Do instead:** ship a bounded ordered parallel map and fixed-grouping or law-checked reduction before automatic parallelization, GPU execution, or a new reduction calculus.

[argued] **H2 — `intent.all` is not a complete safe fan-out primitive.** A million independent immutable requests can still exhaust queues and overload a service. Parent cancellation, child failure, supervision, cleanup, and late replies need a scope contract. Exhaustive actor handlers do not prevent deadlock or guarantee progress under overload. **Change my mind:** a fast producer and slow sink stay within fixed memory bounds, children finish or report uncertainty on scope exit, and timers remain responsive under saturation. **Do instead:** add task scopes, bounded concurrent map, mailbox capacities or credits, explicit overload outcomes, and a specified shutdown protocol.

## I — Total programs still need a resource-conscious runtime

[cited] [Chapter 06](../spec/06-runtime.md) promises non-preemptible bounded steps, heap-size-independent reclamation pauses, journaling, replay, simulation, and exploration. It allows reference counting or per-step regions as implementation choices. It does not yet define a complete configuration for exploration or a concrete physical resource bound.

[argued] **I1 — Finite is not responsive.** A terminating exponential computation can monopolize a worker; a finite input can exhaust memory. Reference counting can trigger cascading destruction, while freeing a large region can itself take time. Long-lived machine state cannot simply disappear with a step region. **Change my mind:** large arithmetic, exponential references, deep destruction, and invalid staged evaluation all remain cancellable while another instance meets a latency target. **Do instead:** retain fuel, memory, wall-time, and output limits, permit internal cooperative yielding, and specify bounded reclamation work rather than declaring a memory-management family sufficient.

[measured] The [resource countermodel](experiments/codex-syntax-pilot/countermodels.json) executed `f(0)=1; f(n)=f(n-1)+f(n-1)` at input five and obtained 32. Its call-count recurrence gives 2,147,483,647 calls at input 30, exceeding the declared million-call toy budget. The large case was not executed; that number is analytical, not a timing measurement.

[argued] **I2 — Exploring program state is insufficient.** The same user state can have different pending debits, queues, model states, timers, children, or upgrade epochs, with different futures. Pruning by user-state hash can erase an error path. Finite lists of model answers also do not yet specify arbitrary input signals, which the draft leaves open. **Change my mind:** two equal user states with different pending outcomes both retain their reachable failures, and signal generation has a finite or symbolic search contract. **Do instead:** define the full future-relevant configuration and environment assumptions, and report depth, domains, fairness, and state-space exhaustion with exploration evidence.

[argued] **I3 — Universal journaling has costs and recovery obligations.** Snapshots must preserve pending intents, dispatch state, deduplication retention, witness selection, and model assumptions. A bare hash chain can be rewritten wholesale if no expected head is anchored independently. Journaling every high-frequency event can also cost more than the application work. **Change my mind:** crash tests around compaction and dispatch, increasing-history recovery benchmarks, and durable versus ephemeral p50/p99 latency and bytes-per-operation measurements. **Do instead:** offer explicit durable, replayable-ephemeral, and volatile profiles, with anchored checkpoints and compaction rules that preserve every outstanding operation.

## J — A small checker does not validate its surroundings

[cited] [Chapter 07](../spec/07-compiler.md) calls parsing, resolution, elaboration, optimization, and backends untrusted. It checks core typing and uses finite reference comparisons for arbitrary transformations. [CompCert](https://compcert.org/man/manual001.html) describes semantics preservation as the compiler property connecting source reasoning to execution. [Alive2](https://github.com/AliveToolkit/alive2) specifies symbolic refinement validation with explicit scope limits. These are stronger and more qualified contracts than sampled agreement.

[argued] **J1 — Round trips can consistently preserve a wrong interpretation.** A parser can map printed addition to a subtraction tree while its paired printer reverses the substitution; the round-trip law holds. A resolver can choose a wrong same-typed id; core typing still succeeds. A solver can certify a mistranslated formula. **Change my mind:** malicious parser, resolver, elaborator, and solver-bridge test doubles are rejected by an independent relation to the approved claim. **Do instead:** trust a minimal faithful front end initially, or check translation certificates tied to independently rendered resolved claims; require proof reconstruction to establish the original obligation, not merely the solver query.

[argued] **J2 — Sampling does not transfer universal source proofs to binaries.** A backend can agree on every example, generated input, and recorded journal, then disagree elsewhere. Procedure lowering and resource metering also need preservation arguments; optimized physical execution and abstract source costs are not automatically the same accounting system. **Change my mind:** checked transformations or a verified compiler covering the supported subset, suspension, and metering. **Do instead:** label artifact assurance separately from source evidence, trust the initial backend explicitly, and reserve “checked translation validation” for a stated semantic validation method.

[measured] The [backend countermodel](experiments/codex-research/proof-countermodels.json) compared reference `n+1` with a candidate returning `-1` only at `1000`. They agreed at every sampled input `0..31`; at `1000` they returned `1001` and `-1`. This illustrates finite sampling's limit without making a claim about an existing compiler.

[argued] **J3 — The proposed core does not yet express the whole surface.** “First-order” core has `call id`, but surface functions are values, transforms receive them, and nested functions capture bindings. The core lacks an explicit indirect-call and closure-environment account. Meanwhile authority enforcement, persistence recovery, primitive arithmetic, and driver confinement belong to trust even if excluded from a logical kernel count. **Change my mind:** complete lowering of captured, passed, and returned functions with ownership and label preservation, plus a component-by-component trust inventory. **Do instead:** choose a genuinely typed higher-order core or specify checked closure conversion, and publish separate logical, security, execution, and durability trusted bases.

[argued] **J4 — Multiple “readings” are separate analyses with separate domains.** Totality alone does not make an arbitrary function efficiently invertible, incrementally maintainable, generative, or cheap to explore. A compact evaluator does not imply compact proofs for all those transformations. **Change my mind:** useful examples with stated supported fragments, agreement laws, fallback behavior, and measured cost. **Do instead:** ship concrete evaluation and one bounded obligation translation first; add each reading as an optional analysis after its domain and value are demonstrated.

## K — Native UI needs platform semantics beyond drawing

[cited] [Microsoft's UI Automation provider documentation](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-providersoverview) distinguishes standard controls from custom providers. [Text Services Framework](https://learn.microsoft.com/en-us/windows/win32/tsf/text-services-framework) supports multilingual and advanced text input. The reviewed blue-sky chapters do not yet specify a native widget, graphics, or driver ABI.

[argued] **K1 — A framebuffer port is not a complete UI plan.** Building custom widgets includes focus, keyboard navigation, selection, bidirectional text, font fallback, accessibility, DPI, composition, clipboard, and native dialogs. “No webview” does not require owning that entire stack. **Change my mind:** a resizable editor supports Portuguese dead keys, CJK composition, emoji selection, keyboard-only navigation, screen readers, clipboard, and multiple DPI settings through the proposed abstraction. **Do instead:** start with a host-native widget adapter exposing a semantic view tree and normalized events, and provide a separate canvas port for custom graphics.

[argued] **K2 — Deterministic application state is a different target from identical native pixels.** Font metrics, GPU behavior, device loss, DPI, and platform controls enter through the host. Durable logging for each pointer movement or presentation can defeat interactive latency; omitting those inputs changes the replay claim. Wasm also does not imply a browser: a native host can execute it and supply UI drivers. **Change my mind:** the same recorded interaction succeeds on different hosts with declared state, command, layout, and pixel comparison scopes and a measured recording cost. **Do instead:** guarantee deterministic state and normalized view/draw commands, record host-dependent inputs when needed, test pixels only with a pinned renderer, and make high-frequency UI recording explicitly bounded.

## L — Ship a repair loop, not an eighteen-tool catalog

[cited] [Chapter 08](../spec/08-tooling.md) lists eighteen verbs and permits one MCP tool per command; the [tooling note](../tooling.md) argues for few verbs, bounded feedback, and transactions. Its “no sandbox” evaluation claim coexists with invalid overlays, holes, debts, and incomplete resource guarantees. Those contracts need reconciliation before agents evaluate arbitrary staged programs.

[argued] **L1 — Exact first tool set.** A semantic spike can have a smaller interface, but the first useful CLI release must create, format, check, test, run, and package a real command-line program. I propose the conventional CLI below, with a separate small agent catalog over the same engine. Every semantic action accepts a pinned revision or overlay and emits stable ids, schema/tool versions, precise status, bounded text, and a machine-readable envelope.

| Command | Initial contract |
| --- | --- |
| [argued] `init <path>` | Create one pinned package manifest, source file, and runnable CLI example. |
| [argued] `fmt [paths]` | Print canonical source; `--check` reports formatting differences without changing files. |
| [argued] `check [paths-or-names]` | Type/termination checking and explicit proved/refuted/unknown/sampled obligation results. |
| [argued] `test [names]` | Execute selected examples/conformance cases with reproducible seeds, protected expectations, and resource limits. |
| [argued] `run <entry> -- <args>` | Execute a CLI with arguments, stdin, console/files, typed failures, cancellation, and specified exit status. |
| [argued] `build <entry>` | Produce a pinned distributable bundle; initially bundling the reference runtime is acceptable. |
| [argued] `query <mode>` | Modes `show`, `find`, `hole`, and `eval`; bounded inspection/search and file-based evaluation with fuel, memory, time, and output limits. |
| [argued] `stage [paths]` | Stage whole declarations, allow broken intermediates, format on request, return a bounded computed dependency worklist. |
| [argued] `status` | Revision, overlay, worklist, conflicts, and pending approvals; support explicit named discard as a mode. |
| [argued] `publish --expect <revision>` | Atomically admit a local revision/manifest with compare-and-swap and authorization; never implicitly upload it. |

[argued] **L1 continued — Discoverability matters more than verb golf.** Combining all operations into one opaque command can be worse than clear CLI verbs; exposing every low-level action as a separate MCP tool can waste context. The initial agent catalog can contain four operations: `inspect` maps to query/show/find/hole, `verify` maps to check/test, `evaluate` maps to bounded query/eval, and `change` maps to stage/status/publish with an explicit action. CLI execution remains available through the ordinary shell. **Change my mind:** randomized equal-operation tasks comparing this catalog, a smaller catalog, and the draft's catalog, including invented-library calls and cross-file signature repair. **Do instead:** ship the useful conventional CLI and bounded repair loop, a generated versioned one-page language/API card, stable diagnostics and formatter, and expose the four-operation thin adapter only when a client needs it.

[argued] **L2 — Bounded and complete cannot mean all possible context.** Ten thousand broken dependents or a thousand matching values cannot fit in a small diagnostic. “Facts pushed” can become unsolicited noise. A blanket ban on source inside JSON also confuses asking the model to hand-escape source with a client correctly encoding an already generated file. **Change my mind:** high-fanout repair tasks show full pushed context beats ranked summaries, and transport comparisons isolate model generation from mechanical serialization. **Do instead:** return ranked immediate facts, precise remainder counts and cursors; support source files/stdin and mechanically encoded adapters, with PowerShell examples that do not assume Bash redirection.

[argued] **L3 — Evaluation is not an independent oracle.** Promoting an observed wrong answer into an expected example can canonize a bug. Search-for-input and evaluate-with-holes also need explicit unsupported/blocked states and budgets rather than an assurance that purity makes them harmless. **Change my mind:** seeded plausible wrong answers are rejected through separate intent evidence, and difficult searches terminate with useful bounded results. **Do instead:** keep observed fixtures distinct from approved expectations, require intent-authority approval for claim changes, and preserve provenance and resource limits throughout the session.

## M — Collapse representations without erasing obligations

[cited] [Chapter 01](../spec/01-programs.md#cells) lists thirteen cell kinds. A common tree representation does not make their laws the same. The following cuts target exposed concepts and initial implementation scope rather than claiming that one keyword solves every distinction.

| Current concepts | Proposed first treatment |
| --- | --- |
| [argued] Claim, witness, evidence | Keep contract/body separation and evidence records, but do not require three separately authored documents for routine definitions. |
| [argued] `fn`, `lemma`, `law` | Reuse declaration/context machinery; attach proof-only assertions and interface laws without erasing their non-executable proof semantics. |
| [argued] `proc`, `machine` | One runtime transition representation; direct-style procedures as sugar and explicit machines when state/event structure is useful. |
| [argued] `machine`, `model` | Reuse reducer infrastructure; preserve the distinction between actual application behavior and nondeterministic environment choices. |
| [argued] `interface`, `port` | Reuse operation schemas; preserve capability possession and effect authority as separate judgments. |
| [argued] `target` | Initially versioned manifest data, not another language declaration. |
| [argued] Examples, debts, evidence | Attached records with provenance and policy, not independent surface languages. |
| [argued] `notation`, tables, `protocol` | Defer; generate ordinary code or views first, then add checked syntax only for demonstrated domains. |

[argued] **M1 — The smallest surface can still hide a large language.** A universal `cell` with many mode flags merely moves distinctions into attribute combinations. Likewise calling elaborating total functions “not macros” does not remove expansion, hygiene, error mapping, or versioning responsibilities. **Change my mind:** a reduced design expresses the same useful workload with fewer rules and equal diagnostic quality, rather than just fewer keywords. **Do instead:** count semantic judgments, legal combinations, required author decisions, and grammar-card size; keep distinctions that enforce different guarantees and defer mechanisms with no first workload.

[argued] **M2 — Canonical syntax should not forbid harmless structure for its own sake.** Renamed closers, a fixed nesting depth, mandatory local annotations, no anonymous functions, and type-dependent labels combine into a substantial memorized protocol. “One way” is valuable only when the chosen way remains economical across tasks. **Change my mind:** ablations show each rule independently improves completed correct changes after its instruction cost is included. **Do instead:** retain canonical formatting, explicit public boundaries, and a minimal grammar, while treating the remaining restrictions as hypotheses.

## N — Build a useful CLI before a universal runtime

[argued] **N1 — The proposed layers are not independent products.** A pure store language without useful input/output can pass its own corpus while failing to deliver the owner's first priority. Conversely, a durable service release already needs authority, resource controls, recovery semantics, and enough evidence policy; deferring those leaves promises unsupported. **Change my mind:** a concrete user completes a real CLI task and then a reusable-library task, with guarantees stated precisely and packaging tested on a clean machine. **Do instead:** make the first release a file-validation/transform CLI with arguments, stdin, console, scoped files, typed errors, and exit status, then add a bounded parallel-hashing task and extract its reusable library before advancing to services.

| Experiment/release gate | Deliver | Cut until the gate earns expansion |
| --- | --- | --- |
| [argued] Gate 0: choose Vibra's smallest architecture | Protected task corpus, executable semantic spike, matched baseline, and author/human-review cost measurement. This is an experiment, not a useful release. | New authoritative store, general notation, UI toolkit, distributed runtime. |
| [argued] Gate 1: useful CLI release | One surface, nominal positive data, functions/transforms, restricted totality/refinements, scoped console/files, arguments/stdin/exit status, explicit errors, format/check/test/run, pinned dependencies, simple build bundle. | Mandatory durability, general dependent types, automatic cost inference as a guarantee, security claims beyond the stated profile, extra readings. |
| [argued] Gate 2: reusable libraries and easy local parallelism | Extract the validation/transform library, package it, document readable claims, add bounded parallel map/hashing, and verify identical serial/parallel outcomes and bounded resources. | Distribution, custom graphics, arbitrary handlers, protocols, unrestricted linear persistence. |
| [argued] Gate 3: services and optional durable workflow | Scoped tasks and overload handling; then one journal/sequencer, durable dispatch/outbox, uncertainty/reconciliation, models, crash injection, replay, and versioned upgrades. | Replicated journals, unrestricted hot upgrades, universal model checking, automatic performance claims; native UI remains a future separate slice. |

[argued] **N2 — A finishable architecture needs stop rules for mechanisms.** Removing implementation size from the decision order makes complexity outside the kernel appear free, but someone must maintain tools, runtime, libraries, schemas, and proofs. The strongest model today is not a permanent author profile. Vibra's existence is fixed; the full proposed substrate is not. **Change my mind:** a costed schedule with maintainable ownership, an independently reviewable core, and useful results under more than one model configuration. **Do instead:** choose prototype time/compute budgets and acceptable defect/cost tradeoffs in advance, stop unsuccessful mechanisms when budgets expire, and build the simpler Vibra profile supported by the evidence.

## O — Add evidence quality to the agenda

[argued] **O1 — The protocol's provenance ranking cannot decide truth.** A citation to an unrelated benchmark or a biased one-participant measurement cannot outrank a direct counterexample to a universal claim. “LLM evidence decides” also needs an objective: faster code, fewer escaped defects, easier human review, security, and implementation cost can conflict. Their weights do not emerge from a model vote; the owner's priority order resolves some scope but not every tradeoff threshold. **Change my mind:** preregistered tasks, interventions, evaluation criteria, uncertainty, and a decision rule reflecting the intended CLI-first product. **Do instead:** keep the tags, rank relevance and validity, let counterexamples refute universals, and fix the remaining acceptance thresholds before inspecting results.

[argued] **O2 — Avoid correlated judges and benchmark leakage.** Two reviewers or several agents sharing a model family do not provide cross-model replication. Reusing solved examples, allowing the implementation to write its judge, or treating a finite toy pilot as a general success rate would reward conformity. **Change my mind:** independent held-out tasks, protected evaluators, randomized surface assignment, and replication across model families when available. **Do instead:** preserve raw prompts, first outputs, harnesses, seeds, repairs, costs, and failures, and label unreplicated results exactly as such.

## P — Add persistence and evolution to the agenda

[argued] **P1 — Witness replacement is not automatically a safe live upgrade.** A procedure's suspended frame depends on its witness's control flow and captured bindings. Replacing that witness can change suspension points without changing its public claim or user-declared state type. Outstanding outcomes and old idempotency keys still refer to an earlier execution. **Change my mind:** a suspended procedure upgrades across reordered awaits and changed locals, survives restart, and preserves pending-operation identity. **Do instead:** pin code epochs for running instances by default, version durable frame schemas, and require explicit migration or restart rules for supported live upgrades.

[argued] **P2 — Canonical hashes need versioned semantics.** Encoding, normalization, nominal brands, primitive arithmetic, float rendering, Unicode handling, closure representation, driver ABI, and evidence schemas can evolve independently. A content hash without its interpretation version is not enough to reproduce an old execution. **Change my mind:** an older package and journal remain inspectable and reproducible after a toolchain/schema upgrade with intentional incompatibilities reported precisely. **Do instead:** version each persistent contract, include semantic versions in manifests/cache identities, and specify deliberate migration and unsupported-version behavior before claiming permanent reproducibility.

## Q — Add ecosystem and deployment to the agenda

[argued] **Q1 — Drivers can become the entire useful ecosystem.** If every database, network stack, graphics API, and foreign library requires a bespoke driver plus executable failure model, integration cost can dominate language benefits. Requiring a model is useful only if its abstraction is expressible and maintained. **Change my mind:** one real dependency is integrated, upgraded, fault-simulated, and packaged without a large custom trusted layer. **Do instead:** specify one narrow versioned host ABI, reusable driver/model schemas, and explicit trust labels for incomplete models; count integration work in comparisons between Vibra architectures and existing-language baselines.

[argued] **Q2 — Package correctness is not deployment security.** Hashes identify artifacts, not who should be trusted to supply them. Reproducible builds, provenance, offline resolution, dependency policy, and driver permissions remain operational requirements. **Change my mind:** a clean Windows machine resolves pinned dependencies, builds, runs, and reproduces evidence without undeclared host state, while a malicious replacement is detected. **Do instead:** ship a minimal pinned package/build manifest and dependency trust policy with the first usable profile, and postpone a registry until local/offline packaging works.

## R — Add journal confidentiality and retention to the agenda

[argued] **R1 — Complete replay and limited retention are competing requirements.** Journals can duplicate secrets, personal inputs, large assets, and obsolete code. Encrypting a payload is insufficient if metadata reveals labels, event timing, sizes, or stable hashes. Omitting protected fields from an export can make it non-replayable. Reachability-preserving append-only storage also needs a deliberate lifecycle policy. **Change my mind:** secret-bearing traces are exported, redacted, compacted, rotated, and deleted under a stated policy, with every remaining replay guarantee checked. **Do instead:** classify journal fields and metadata, define encryption/key ownership and retention, distinguish replayable from redacted exports, and state exactly which reproducibility guarantees are surrendered on deletion.

[argued] **R2 — Counterfactual replay must remain separated from production effects.** A replay branch using old identities against a real driver can duplicate or confuse effects; a model result can be mistaken for production evidence if provenance is weak. **Change my mind:** attempts to route simulation, what-if, or imported journals to production drivers fail unless an explicitly authorized target establishes fresh operation identity. **Do instead:** make simulation/replay execution modes and credentials disjoint, carry mode and model provenance in artifacts, and default counterfactuals to isolated models.

## Questions for Round 2

[argued] The first dispute is which small Vibra architecture best serves a useful CLI, with existing languages as baselines and human claim comprehension included in the score. Fix a common workload and budget before expanding the feature list. The second is the safety boundary: which obligations require universal evidence, which retain runtime checks, and what exactly lower grades authorize. The third is authority: specify resource capabilities and latent intent effects before claiming least authority. The fourth is cancellation and recovery: agree on the complete operation lifecycle before implementing journal combinators for later services.

[argued] Then run the larger syntax experiment, the bounded parallelism/overload slice, and the faithful-translation attacks. Preserve the keyword-delimited alternative as a serious contestant; this round found no winner. Require a native text/accessibility slice before committing to custom UI, and a suspended-frame migration test before promising witness hot-swapping. These are the experiments most likely to change the architecture rather than merely tune its spelling.
