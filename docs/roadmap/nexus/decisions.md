# Nexus decision ledger

The record of what was decided for Nexus, by whom, why, and what was turned
down. It follows the [M4 ledger](../v0.0.1/m4/decision-ledger.md)'s
dispositions:

- **decided** — made by the maintainer, Hannah, with the date;
- **recorded** — an implementation decision taken while writing the design on
  2026-11-11. It is not a language rule. Hannah has not reviewed it, and it
  stands until she revises it;
- **proposed** — needs specification text, so it is not in force until the
  named package lands it with Hannah's approval;
- **open** — a question only Hannah can settle. One remains: O4, in the
  [last table](#answered-by-hannah).

Every row names the package that proves it. A package that finds a row wrong
stops and reports; it does not work around the row.

## Decisions

| ID | Disposition | Decision | Why, and what was rejected | Proof owner |

| N1 | decided, Hannah, 2026-11-11 | v0.0.3 and v0.0.4 start now, in parallel, ahead of the v0.0.2 exit gate. Wasm integrations may be broken where they block this work; removing Wasm is not this track's goal | The releases overlap only at the Wasm deprecation. This overrides [roadmap rule 1](../README.md#roadmap-rules) for this track only. Rule 3 still holds: nothing here is advertised by the CLI or the schemas, and it reaches `main` only as a coherent change. As of the foundation, no Wasm code was touched | The inherited-item table of [goals.md](goals.md#inherited-from-v002-m5); X3-26 owns removal |
| N2 | recorded | Frames live in runtime memory and every call returns to a dispatcher. Generated functions are resumable: a switch on the frame's resume block | The charter and the runtime chapter forbid host stack per activation and require tail transfer to *any* callee. The scratchpad asked for the comparison with a native-stack design. That design fails three ways: deep recursion needs segmented or switched stacks, which is per-OS `unsafe`; a tail transfer to an indirect callee with a different frame needs a guaranteed tail-call convention on every target; and a yield or a v0.0.4 park needs a stack switch, where here a frame *is* the suspended state. M4 D2.11 proved this shape on Wasm. The cost is one dispatcher round trip per call, measured in X3-22 and attacked only after parity | Foundation: `non_tail_recursion_is_bounded_by_memory_and_uses_no_native_stack`, `tail_transfers_keep_the_frame_count_and_the_live_size_bounded`. X3-09 natively |
| N3 | proposed (X3-S1) | Checkpoints are exactly the five transfers. Quota counts checkpoints plus charged proportional work, is a runtime scheduling control, and is unobservable. A primitive is atomic with respect to yielding and charges after it completes | The charter excludes language-defined fuel, so quota must not be a language outcome; making it unobservable keeps that true and makes "yield everywhere" a complete test. Resumable primitives were rejected for v0.0.3: M2 asks for yields *around* long primitives, and mid-primitive state would be new suspended state outside the frame | Foundation: `yielding_at_every_checkpoint_changes_no_observation`. X3-21 for the corpus |
| N4 | recorded | The execution IR is its own crate with its own verifier. It reuses the closed registries of `vibra-ir` (`CompilerIntrinsic`, `HostRow`, `TrapCode`) instead of restating them. Slot ownership is part of what is verified | "Verify layouts and transfers before emission" needs a thing to verify. Lowering straight to Cranelift, as the Wasm backend lowers straight to bytes, was rejected: it would leave no place to check, and no way to test a lowering without a linker. Reusing the registries keeps one closed table | Foundation: `crates/vibra-exec/tests/it` (V1–V6) |
| N5 | recorded | Nexus does not depend on the execution IR or on a code generator. Every transfer is a `Context` method written once; `Code::step` is the only thing an executor implements | The runtime archive linked into user programs must not carry a compiler IR. One implementation of push, replace, pop, and host dispatch is what makes the stepper's evidence transfer to generated code | The `vibra-nexus` row of `architecture_boundary` |
| N6 | recorded | A reference stepper executes execution IR on Nexus. It is a toolchain test instrument: no CLI command, no conformance profile, no build product. It rejects a program it cannot run in full | It splits "native parity" into a lowering comparison and a code-generation comparison, gives every platform the first one, and gives delegated code-generation work an oracle per instruction. Without it the first observable result needs lowering, codegen, bridge, archive, and linker all working on Windows at once. The cost is one more executor to keep in step, bounded by the extension rule of [design.md](design.md#verification-rules) | Foundation: `crates/vibra-nexus-eval/tests/it`. X3-04 for the corpus |
| N7 | recorded | The value store is a context-local byte arena with the M4 layout of `vibra_ir::arena`, 32-bit offset handles, and precise reference counting with a worklist release. A native program has no host value IDs and no handle table | The layout is proven, `vibra-native` already reads it, and it is safe Rust over a `Vec<u8>`. Offsets are context-local and relocatable, which is the "opaque context-local handle" v0.0.4 inherits. Native pointers were rejected (unsafe everywhere, not relocatable); a graph of `Rc` objects was rejected (generated code could never read it, and the native code would need a third value interface). IDs exist in Wasm because the host is outside the module; here it is in-process Rust. **Limit:** one context holds at most 4 GiB (see O9) | Foundation: `vibra-nexus` store tests. X3-02 ports the M4 arena tests |
| N8 | recorded | Frames live in a cell stack the context owns, beside the store and charged against the same limit | Simpler than M4's frame segments inside the arena, and the limit still covers recursion. The runtime chapter says activations are held in "the arena"; X3-S1 rewords that to the instance's own storage, which is what the rule needs | Foundation: `exhausting_the_limit_is_the_host_event_and_a_larger_limit_recovers`. X3-S1 for the wording |
| N9 | recorded | A function value is `[function][slots][params][captures…]`; a call through it checks the operand count and passes the value as the callee's environment; a module function used as a value gets a wrapper body | M4 D2.14, restated for the new IR. One call mechanism serves closures and module functions | Foundation: `a_function_value_called_with_another_arity_is_a_toolchain_defect`. X3-14 completes the header |
| N10 | proposed (X3-S1 for the ABI contract) | The workspace keeps `unsafe_code = "forbid"`. Exactly one crate, `vibra-nexus-bridge`, declares its own lint table and contains every `unsafe` block and every `extern "C"` item. An architecture test names it | #408 asked for raw-pointer code in one reviewed bridge. A crate boundary is the only lint scope `forbid` allows, and it makes the audit of G3.M3.6 a single directory | X3-05: the architecture test and the bridge audit |
| N11 | recorded | Baseline generated code calls a runtime routine for every value operation and names slots by index. No pointer into the store or the cell stack crosses the bridge | Layouts stay private to one crate, the bridge stays small, and correctness comes before speed, as "Determinism and observability" requires of optimization. M2 records the unoptimized baseline; inlining slot access is the first measured optimization after it | X3-06; X3-22 measures |
| N12 | recorded | Cranelift is pinned to the version Wasmtime already locks (0.136.x at 2026-11-11) while both are in the tree, and only `vibra-codegen` depends on `cranelift-*` | One Cranelift in the lock file, and the M4 rule "only the runner depends on the engine" carried over | X3-06: lock file and architecture test |
| N13 | recorded | The runtime ships as one static archive per target built from the bridge crate, with the launcher's `main` inside it. The linker is located explicitly per platform, never through `PATH` | #408 chose a statically linked runtime archive. On the development machine `link.exe` on `PATH` is BusyBox, so a `PATH` lookup would fail or, worse, find the wrong tool | X3-S2 records feasibility; X3-07 |
| N14 | proposed (X3-S1) | During the transition one expectation is compared against up to four executors, and `conformance/native-parity.tsv` tracks each executable case per executor as `matched` or `pending <package>`. `pending` never passes a gate | G3.M1.12 requires the remaining corpus recorded by feature and platform. The specification now says the Wasm backend has no skipped-case table; the transition profile must say the native one does until M2 exits | X3-04 creates it; X3-22 empties it |
| N15 | recorded | Generic code receives type descriptors at run time. No monomorphization in v0.0.3 | Same choice as the interpreter and M4 D9.2, so the lowering ports instead of being redesigned. Monomorphization is an optimization to measure later | X3-13 |
| N16 | recorded | Observation (canonical encoding, `assert.equal`, audit arguments) is Rust inside Nexus producing `vibra_ir::ObservedValue`. Nothing is generated into the program for it | The Wasm backend had to emit a canonical walker (`canon_typed.rs`, M4 D8.4) because its host was outside. Here the runtime is Rust beside the values, so the interpreter's encoder is reused and cannot drift | X3-18 |
| N17 | recorded | Native test execution exists for parity only. The program descriptor carries a test table that the harness launcher uses; `vibra test` stays on the interpreter | G3.R7, and G3.M2.2 still compares test outcomes | X3-18 |
| N18 | recorded | The launcher has a shipping `system` profile and a `harness` profile that exists only in the test archive, takes a host world and a quota, and writes one observation document. That document is internal and unversioned | G3.M2.2 needs deterministic worlds *and* real process launches. A world switch in the shipped launcher would be a mode the runtime chapter says the language does not have | X3-05, X3-09 |
| N19 | proposed (X4-S1) | The actor kernel is one backend-neutral crate that both executors drive | The parity strategy that worked for host operations and natives: one implementation, so the interpreter and Nexus cannot disagree about ordering, bounds, scope checks, or exit | X4-01, X4-03, X4-05 |
| N20 | proposed (X4-S1) | One Nexus context per actor. Messages are copied between stores through a neutral value. Addresses are a new closed value kind | Share-nothing makes single ownership structural and keeps counts non-atomic. Sharing immutable buffers across contexts was deferred: it needs atomic counts or a second heap, and nothing has measured the copy yet | X4-05 |
| N21 | proposed (X4-S1) | A schedule is the sequence of kernel decisions taken at kernel actions. Replay does not depend on quota or reduction counts | The concurrency scratchpad wanted identical reduction counts in both backends. That would couple the interpreter's evaluation steps to the native checkpoint structure forever. Since an actor's state is private, only the order of kernel actions is observable | X4-01, X4-04 |
| N22 | proposed (X4-S1) | A fixed worker pool; an actor is pinned to its worker before initialization; no stealing or migration; mailboxes use `std` synchronization | G4.6 asks for placement before initialization and rules migration out. It also keeps the scheduler free of `unsafe` | X4-07, X4-09 |
| N23 | recorded | `Step` and `Outcome` are `non_exhaustive`, and status code 4 is reserved for `Wait` | v0.0.4 adds waiting without reshaping the boundary | X4-05 |
| N24 | recorded | This plan lives in `docs/roadmap/nexus/`, at the roadmap's authority level, and spans two releases. Milestone step tables in `v0.0.3/m*/README.md` are written from it when each milestone's integration branch is bootstrapped | The execution model wants a step plan per milestone; Nexus needs one design across milestones. Both exist, and this one is the source | The bootstrap PR of each integration branch |
| N25 | decided, Hannah, 2026-11-11 | A rule, representation, or provider shape that existed only because of WebAssembly may be changed freely where native execution makes it pointless. This extends N1 | The host registry, the provider split, and several runtime-chapter rules were shaped for a Wasm module with an outside host. A package that finds such a rule in its way names it, proposes the change in the specification package it belongs to (X3-S1 or X4-S1), and does not preserve it for compatibility. The interpreter stays the oracle | X3-S1, X4-S1 |
| N26 | decided, Hannah, 2026-11-11 | Sandboxing is not a goal of this track for now. The claims and limits of the runtime chapter stand: effects are static and erased, the runtime takes no grant table, and Nexus adds no policy check | Asked on PR #413. Recorded so a later review starts from what is true today: root-level confinement holds only for source compiled by a trusted toolchain; a native executable from elsewhere has no guarantee; a fine-grained policy needs a runtime check at `Context::host`, the single place every host operation passes. It returns with O4 | — |
| N27 | recorded, to be fixed in X3-03 | Verification bounds a function's frame: `slots` may not exceed a fixed maximum (`MAX_SLOTS`, 65,536), rejected as a new `FrameTooLarge` kind before any per-block state is allocated | Found by X3-01: the verifier allocates one state per declared slot per reached block, so a program declaring billions of slots makes verification itself attempt a multi-gigabyte allocation. The verifier is the admission check for untrusted execution IR and must be total in bounded memory. The number is a toolchain limit, not a language rule; a lowering that needs more is a design gap | X3-03: a rejected program for the kind |
| N28 | recorded, for X3-26 | The size-class bounds (MIN_CLASS, MAX_CLASS) move from ibra_wasm::layout into ibra_ir::arena at cutover; until then the store keeps its own copies | Found by X3-02: they are the one part of the M4 layout the store could not import | X3-26 |

## Answered by Hannah

Answered on PR #413, 2026-11-11. A question with no comment was agreed as
proposed. **O4 is still open.**

| ID | Question | Answer | Lands in |
| --- | --- | --- | --- |
| O1 | Is an actor a turn-based handler over carried state or a receive loop holding an inbox? | **Receive loop.** "Concurrency is a dependency for true actors." An actor's activation therefore parks inside a receive, so `Step::Wait` (N23) is the ordinary path of every actor and not only of a blocked caller. Where the v0.0.4 roadmap says "one message handler at a time" and "state between turns", X4-S1 rewrites it | X4-S1 |
| O2 | How does a caller wait for a one-shot reply? | As proposed, read under O1: a waiting activation parks until the reply, the exit, or the timeout | X4-S1 |
| O3 | Is messaging a new provider, new `@host` rows, or a language form? | **Free to redesign.** Vibra is to be actor-first: X4-S1 may redesign language forms, and may redesign the providers, which were shaped for Wasm (N25). The charter change is expected | X4-S1 |
| O4 | What does issuing a narrower address look like in source, and what is a "resource scope" in the type system? | **Open.** Hannah has no answer yet. Requirements she stated: bounds must be expressive enough for "network requests to a specific set of endpoints, with a specific protocol and specific verbs" and "read-only access to just `.txt` files under a folder the user provides at runtime"; that points to policies, capabilities, and effects being compound and expressed as values in a DSL that does not pollute the code. Until settled, the kernel keeps the scope check behind one function so its representation can change | X4-S1, X4-02 |
| O5 | Does the specification mention quota and yielding? | As proposed: it states only that execution may be suspended at checkpoints without observable effect. Quota stays a toolchain term | X3-S1 |
| O6 | The CLI shape of native build | As proposed: `vibra build <target> --target <triple>`, host triple by default, another triple is a new unsupported-target diagnostic | X3-S1, X3-23 |
| O7 | CI for Linux x86-64 and macOS arm64 | As proposed: every PR for Windows, the draft PR for the other two | X3-S2, X3-08 |
| O8 | May the baseline unbox `bool` and other all-`void` enums? | As proposed: no, until the baseline is measured | X3-22 |
| O9 | Is a 4 GiB ceiling per context acceptable for pre-alpha? | As proposed: yes | X3-02 |
| O10 | Does the M1 "indirect cross-module tail call" need two modules or two packages? | As proposed: two modules of one package | X3-09 |
