# Roadmap to a usable Vibra v1

Status: normative delivery plan
Implementation status: milestone 1 merged through PR #283; milestone 2 implementation is integrated through Step 10 on `m2`
Last updated: 2026-09-23

Milestone work is decomposed, branched, and tracked as described in
[the milestone execution model](execution.md). Active step plans live in
`docs/roadmap/milestone-<n>/`.

## Roadmap rules

This roadmap rebuilds from the active specification. It is not a migration of
the archived compiler.

1. A milestone starts only after the previous exit gate is evidenced.
2. Work lands as vertical, conforming slices. Parser-only, runtime-only, and
   docs-only versions of a promised feature do not count as completion.
3. Main stays coherent. Incomplete features remain on short-lived branches and
   are not advertised by the CLI or schemas.
4. Every rule lands with host-language tests, Vibra conformance cases,
   diagnostics, machine schemas, and canonical documentation as applicable.
5. No pre-v1 compatibility parser, lowering adapter, CLI alias, schema field,
   ABI shim, or automatic migration enters the new implementation.
6. When implementation exposes a design gap, specification review happens
   before more code.

## Architecture boundary

The implementation begins as a new Rust workspace with dependency direction:

```text
syntax -> resolved AST -> typed IR -> interpreter
                              |          |
                              |          +-> external registries/adapters
                              +-> Wasm backend

workspace service -> syntax/resolution/types/effects
CLI and MCP -> workspace service and execution entrypoints
```

There is one lossless syntax tree, one resolved typed IR, one diagnostic model,
one effect-bearing function-call graph, and one workspace snapshot service.
The interpreter and Wasm backend consume the same typed IR. CLI and MCP are
adapters, not alternate implementations.

Crate/module boundaries may evolve, but dependency arrows may not point from
language semantics into CLI, MCP, filesystem UI, or a backend.

## Milestone 0 — freeze the product contract

Outcome: contributors can answer exactly what v1 includes without reading old
code.

Deliverables:

- active v1 charter and seven topic specifications;
- explicit v1 exclusions and compatibility policy;
- this ordered roadmap and release gate;
- complete pre-v1 tree under `archive/pre-v1/` with a commit and submodule
  restoration pointer; and
- active contribution guidance that makes the specification authoritative.

Exit gate:

- no active document claims a compiler or CLI currently exists;
- every v1 surface maps to one canonical chapter;
- examples and terminology agree across chapters;
- archive links resolve and no archived document appears in the active index;
  and
- maintainers approve the v1 boundary before implementation starts.

## Milestone 1 — reader, formatter, and conformance spine

Outcome: an incomplete `.vib` file can be parsed, diagnosed, formatted, and
queried structurally.

Deliverables:

- new Rust workspace and CI without archived dependencies;
- UTF-8 lexer, lossless recovery CST, spans, native top-form AST nodes, and
  nested interface-implementation nodes;
- explicit `.vib` source and `.vibon` data document modes over the shared
  lexer, with no content sniffing or extension fallback;
- `void`, EDN-style Unicode character literals, decimal numeric literals, and
  exact `i8`-through-`i64`, `u8`-through-`u64`, `f32`, and `f64` suffixes;
- complete qualified-kebab symbol grammar, derived labels and atoms, and
  discard semantics;
- general lists with arbitrary head forms, flat pattern/type parameters,
  flat record/enum pairs, flat union member lists, flat match arms, and flat
  declaration syntax;
- the `as` reserved form in expression and pattern head position, recognized
  before the general application and constructor-pattern productions;
- canonical, idempotent formatter;
- named atom diagnostic data model, built-in level registry, and initial
  CLI/MCP JSON Schemas;
- spec-rule-addressed conformance runner; and
- structural source-position query metadata for grammar categories and allowed
  labels.

Exit gate:

- reader positive/negative/recovery corpus passes;
- every syntax example is classified and exercised;
- formatter round-trip and idempotence properties pass, including tolerant
  labelled/variadic normalization;
- Unicode byte and display spans pass; and
- a configured fuzz campaign finds no panic or non-idempotent accepted input.

## Milestone 2 — executable pure core

Execution plan: [M2 steps and implementation guides](milestone-2/README.md).
Integration branch: `m2`, created from `main` after the M1 merge. Each numbered
step lands through one PR into `m2`. Step 1 closes the explicit subset,
bootstrap, diagnostic, and machine-contract prerequisites before dependent
implementation. Until the implementation steps land, this branch freezes the
boundary, signed offline bootstrap provenance, assertion outcomes, and trap
envelopes, and claims no executable M2 support; valid deferred v1 forms use
the canonical `@tool.unavailable` result rather than a profile-specific
dialect.

Outcome: `vibra project init`, `fmt`, `check`, `test`, and interpreter-backed
`run` work for pure programs.

Deliverables:

- `@project.v1` record decoder, source graph, explicit atom-entity import
  resolver, `project.vibon` discovery, and namespaces;
- unit-rooted atom path resolution shared by imports and the `entry`
  declaration reference, enforced leaf-or-directory module layout, non-nested
  target roots, and decode/resolve phase separation;
- primitive types including `char` and the fixed-width numerics, `def`,
  functions, `lambda`, immutable bindings/values, general application with the
  `fn` category, direct local-name patterns, `do`, `if`, recursion with
  mandatory tail calls, first-class function paths, and closed `@compiler`
  externals;
- resolver-enforced no-shadowing and explicit visibility;
- binding and wildcard discards that create no identity and may repeat;
- rejection of every provider other than `@compiler` and `@host`, including
  source-level Wasm FFI;
- rejection of retired `while`, `for`, `break`, `continue`, and `return` forms;
- typed IR and reference interpreter;
- pure core standard library and test assertions; and
- type-aware source-position metadata for visible names and expected primitive
  types.

Demo gate: initialize and run a pure multi-module program, then run its tests
from a clean checkout with no network or host operations.

Exit gate:

- static and interpreter conformance profiles pass for the implemented subset;
- no compiler phase depends on CLI/MCP representations;
- pure execution emits no host event and cannot observe ambient state through
  conforming source;
- tail-position recursion does not grow language-level stack in the reference
  interpreter; and
- unsupported later-v1 forms receive explicit availability diagnostics rather
  than being misclassified as generic applications.

## Refinements to milestones 3 through 7

Milestone numbers 3 through 7 are stable identities. M2 plans, decision
ledgers, the supported-surface table, and implementation diagnostics already
assign deferred work to them by number, so later milestones are refined by
internal **stages**, never by renumbering or inserting a milestone.

A stage is a planning checkpoint inside one milestone's integration branch.
It has its own demo and corpus sub-gate so that a long milestone produces
evidence early, but it is not merged to `main` on its own. The milestone exit
gate remains the only merge gate, as the execution model requires.

The refinements below were made after M2 exposed three delivery risks:

- **M3 was a single very large gate.** It is split into a data-and-failure
  stage and an abstraction stage, and the M2 deferral ledger is made an
  explicit exit clause.
- **The M4 exit gate required interpreter/Wasm parity before any milestone
  delivered a Wasm backend.** The Wasm lowering spine now lands as the first M4
  stage, so the `@host` ABI is designed while both backends exist. M7 keeps
  build products, packaging, audits, and the release.
- **M5 moved the standard library to an ordinary pinned dependency without
  saying what then authorizes its `@compiler` and `@host` declarations.** M5
  now starts by closing that trust contract.

Post-v1 direction, which these milestones must not implement but should not
foreclose, is recorded in [Beyond v1](beyond-v1/README.md).

## Milestone 3 — complete nominal static core

Outcome: authors can build reusable, strongly typed pure libraries.

Deliverables:

- records, enums, newtypes, tuples, arrays, flat maps, and atoms;
- closed constructor/projection/lookup application for products and
  collections, including `tuple.of`, `array.of`, and `map.of` value
  construction and optional bounds/presence lookup;
- flat `where:` generics with `deftype`-inherited names in nested methods,
  closed `impl` targets, complete `types:` call-site argument lists taken from
  the addressed entity, the predeclared empty interface `any` and interface
  values in type position, interface default methods that cannot be overridden,
  `fn` types, `lambda`, `impl` blocks nested in the owning `deftype` or
  `defint`, static dispatch, and ownership/conflict rules;
- unqualified declaration names in every nesting position, path-based method
  and contract references at use sites, one flat addressable-member namespace
  per owner, same-module `impl` rejection, and type-keyed implementation
  identity spelling an `impl` block as applied-target/receiver-type and a member
  as contract-member/applied-target/receiver-type;
- exhaustive flat-arm `match`, `option`, `result`, `try`, and unhandled-failure
  checks;
- nominal `deftype` unions over a closed, pairwise non-unifiable member set,
  with no lifted members and no flattening;
- a `deftype-body` grammar position restricting `record`, `enum`, `union`, and
  `newtype` to declaration bodies, plus a `type-name` applied-type head
  excluding every reserved type head, so no anonymous or structural form of any
  of the four is spellable in a type position or reachable as an application;
- bound-agnostic unification behind every overlap rule, so overlap is decided at
  the declaration and never changes with a distant `impl`;
- all three widening relations — to an interface, to a union, and from an atom
  singleton to `atom` — fired only from written expected types, with no
  computed least upper bound, plus `as` ascription and `as` union narrowing in
  `match`;
- destination-dispatched contract members covering conversion and factory
  shapes alike, the `from` and `try-from` interfaces, the `conversion-error`
  standard-library enum, and one receiver implementing a generic interface at
  several pairwise non-unifiable applied targets;
- destructuring patterns in `let`, fixed positional parameters, lambdas, and
  `match`, with shared exhaustiveness-based irrefutability and no `(bind ...)`
  compatibility form;
- the standard `iter` interface with abstract `next`, canonical default methods,
  closed registry conformance for `(array t)`, `(map k v)`, `str`, and
  `(option t)`, and stdlib adapter types `mapped-iter`, `filtered-iter`,
  `skipped-iter`, and `taken-iter` with explicit `impl (iter item)`;
- function types with closed effect rows, initially empty for the pure slice;
- full resolved symbol/reference/index records;
- a core/text/bytes/collection/option/result standard-library foundation,
  including the checked integer operations (`integer.add-checked` and its
  siblings) whose nominal `result` contracts M2 left unavailable; and
- written algebraic laws for the standard `equatable`, `ordered`, and
  `hashable` interfaces and for the `iter` default methods, stated in their
  documentation and exercised by conformance examples. The laws are not yet
  checked obligations; stating them now keeps a post-v1 law-checking track
  from retroactively invalidating v1 implementations.

### Stage 3A — nominal data and typed failure

Records, enums, newtypes, unions, tuples, arrays, maps, atoms, their
constructors, projections, and lookups; variadic collection operands;
destructuring and constructor patterns; exhaustive `match`; `option`, `result`,
`try`, and unhandled-failure checks; union widening, `as` ascription, and `as`
narrowing; the checked integer and core collection standard library.

Stage demo: a pure module parses a small line-oriented format into a nominal
record/enum model, reports failures through a nominal error union with `try`,
and is tested exhaustively, with no generics or interfaces.

### Stage 3B — interfaces, generics, conversion, and iteration

`where:` generics and `types:`, `defint`, nested `impl` blocks and ownership,
default methods, `any` and interface values, interface widening,
destination-dispatched members, `from`/`try-from`, `iter` with its closed
builtin conformance and adapter types, and the resolved symbol/reference index.

Stage 3B begins with one specification review: the `iter` default `map`
signature `(fn (item) item)` cannot change the element type, although a nested
method may declare its own generic names. The review either records why
element-type-preserving `map` is intended or amends the type chapter to a
`where: (out any)` result of `(iter out)` before implementation.

Demo gate: implement and test a generic collection-processing library with a
nominal error type, an `iter` implementation, and an interface with a default
method, using no compiler-private escape hatch.

Exit gate:

- the entire type-system chapter has focused positive and negative cases;
- ambiguous inference, illegal shadowing, non-exhaustive matches, invalid
  implementation placement, and silently ignored fallible values produce
  stable atom diagnostics;
- interpreter behavior is independent of map/hash iteration;
- index and context output use canonical resolved identities; and
- every M2 decision-ledger row and supported-surface entry deferred to M3 is
  implemented or explicitly reassigned to a named later milestone, and no
  remaining M3-owned form reports `@tool.unavailable`.

## Milestone 4 — WebAssembly spine, static effects, and host operations

Outcome: Vibra can implement useful local automation with explicit static
effect boundaries and ordinary typed host failures, and every executable
program runs identically in the interpreter and in WebAssembly.

### Stage 4A — WebAssembly lowering spine

The backend spine lands before any host operation so that the `@host` ABI is
designed against both consumers of the typed IR at once, and so that the
parity required by this milestone's exit gate has a backend to measure.

Deliverables:

- unoptimized Wasm lowering from the shared typed IR for the complete pure
  language of M2 and M3, including mandatory tail calls, union discriminants
  in written member order, checked lookups, and `@compiler` externals lowered
  before emission;
- the instance-owned value arena and opaque-index discipline of the runtime
  chapter, exercised with no host import;
- an interpreter/Wasm differential harness over the entire executable corpus;
  and
- byte-identical module output for identical typed programs in one
  environment.

The spine is reached through the conformance harness and an internal test
entrypoint. `vibra build` and `@build.v1` products remain M7 deliverables.

Stage demo: the M3 demo library's tests produce identical results in both
backends, including a deep tail-recursive walk that must not grow stack.

### Stage 4B — static effects and host operations

Deliverables:

- native `deffect` operations, default-empty ceilings, transitively closed
  performed-row checking through effect-operation additive rows,
  imported-symbol effect references, and effect metadata in general queries;
- required binary-target effect arrays and static admission of the resolved
  entry declaration;
- typed `@host` external declarations and closed `vibra_v1` host registry,
  implemented in the interpreter and the Wasm backend in the same change;
- whole-value console, filesystem, environment-read, clock, and random
  operations;
- injected deterministic test providers and ordered audit traces, with one
  versioned audit-event encoding shared by both backends;
- source-position metadata showing performed, enclosing, and target effect rows;
- effectful iteration examples that walk with `iter.next` and tail recursion;
  and
- a recorded performance baseline for the interpreter and unoptimized Wasm on
  the conformance and demo programs, so later regressions are measured rather
  than discovered at release.

Demo gate: a target that declares `@std.fs.read` reads a path chosen at runtime,
transforms the content, and writes to stdout under a declared output root. The
same source is rejected when its function or target ceiling omits a performed
root. No path grant, prompt, or runtime effect check participates. The accepted
program produces byte-identical stdout and audit traces in both backends.

Exit gate:

- an additive root declared on an effect operation reaches the performed row,
  the rejection diagnostic, and the target array of every transitive caller,
  and `@effect.outside-ceiling` names the call witness for each missing root;
- every host operation has one registry entry, owner effect, typed signature,
  and audit-event shape;
- no compiler-generated ambient host read exists outside the registry;
- success, typed host error, propagation, and trap have interpreter/Wasm
  parity; and
- interpreter-v1 conformance passes for the full language, and the Wasm
  backend matches it on every executable case.

This milestone does not claim that effectful programs are host-safe. Runtime
grants, path constraints, budgets, and scoped host handles are outside v1.

The M2 plan summarized Wasm as M7-owned. That summary predates this
refinement: the lowering spine moves here, and M7 keeps build products and
release packaging.

## Milestone 5 — reproducible projects and dependencies

Outcome: real multi-package projects build and test offline from exact inputs.

### Stage 5A — standard-library trust contract

M2 authorizes standard-library `@compiler` declarations through a signed,
repository-owned bootstrap artifact. Delivering the standard library as an
ordinary pinned dependency removes that path, while the charter still forbids
ordinary packages from declaring external bindings. Before dependent
implementation, the programs-and-packages chapter MUST define:

- which exact standard-library revisions a given toolchain trusts to declare
  `@compiler` and `@host` externals, and how that trust is anchored in the
  toolchain rather than in a project file, alias, or package name;
- how a lock records that trust so an offline check can verify it;
- the diagnostics for an untrusted revision that declares externals; and
- the retirement of the M2 bootstrap input, with no silent fallback between
  the two mechanisms.

### Stage 5B — dependencies, lock, and vendor

Deliverables:

- typed `project inspect/add/remove` edit plans;
- exact-revision Git and local dependencies, each alias binding one `@lib`
  target of its package;
- safe atomic vendor sync and canonical `@project-lock.v1`
  `project-lock.vibon` record data;
- workspace hashing, source graph invalidation, and offline enforcement;
- standard library delivered as an ordinary pinned dependency under the
  Stage 5A trust contract; and
- deterministic build-plan `.vibon` data independent of the eventual backend.

Demo gate: sync a diamond-shaped exact dependency graph, disconnect the
network, then check and test it reproducibly. A changed vendor file or stale
lock fails before compilation.

Exit gate:

- path, symlink/junction, vendor, hash, and revision attacks have negative
  tests;
- dependencies execute no install or build scripts;
- clean repeated syncs are no-ops with byte-identical locks;
- a dependency that is not a trusted standard-library revision cannot declare
  an external binding, including through a copied declaration or alias; and
- project changes use the same revision-checked plan engine as source changes.

## Milestone 6 — agent-native workspace tooling

Outcome: an agent can understand and safely change a project without scraping
human terminal text.

Deliverables:

- complete versioned JSON output for all CLI and MCP command results;
- one `query <subject>` interface with metadata projections and relation
  expansions over one snapshot, covering every entity kind introduced by M3
  through M5, including implementations, unions, effect operations, and
  dependency units;
- application-kind metadata and completion for functions, constructors,
  tuple/record selectors, collection indices/keys, and patterns;
- explicit atom-value, entity-reference, and code-reference roles selected by
  source grammar or typed VIBON schema slots;
- transactional format, fix, rename, organize-imports, and project plans;
- CLI preview/write flows with atomic postcondition checking;
- MCP tools mirroring the shared engine; and
- read/write/test/run/sync action separation and workspace confinement.

Demo gate: through MCP alone, inspect a project, discover the expected type and
effects at a location through the same query interface, preview a cross-module
rename, reject a stale apply, and atomically apply a fresh plan. No tool starts
a shell, adds a target effect, or executes code unless its server action is
enabled.

A second, agent-loop demo exercises the purpose of the milestone: starting from
a failing test, an agent uses only query results, diagnostics with safe fixes,
and edit plans to repair the program, and every intermediate write is revision
checked.

Exit gate:

- tooling-v1 conformance passes against CLI and MCP renderings of the same
  workspace results;
- all writes are revision checked, reparsed, retyped, and atomic;
- read-only MCP cannot mutate or execute; and
- JSON producer/consumer tests validate every published interchange schema.

## Milestone 7 — WebAssembly products and v1 release

Outcome: Vibra ships as a complete `full-v1` toolchain.

Deliverables:

- `vibra build` `.wasm` and canonical `@build.v1` `.build.vibon` products over
  the M4 lowering, with the closed scalar-only `@host` ABI;
- deterministic source maps, required-effect metadata, and build fingerprints;
- byte-identical build tests across two clean environments;
- platform packaging for the explicitly supported matrix;
- fuzz, performance, and ABI-boundary audits, with performance compared against
  the M4 baseline;
- release documentation containing only implemented commands and examples; and
- a forward-compatibility review that closes every pre-1.0 decision listed in
  [Beyond v1](beyond-v1/README.md#decisions-to-close-before-10), either by
  changing the v1 specification or by recording why the decision is left to a
  later major version.

Exit gate:

- every requirement in `spec/07-diagnostics-and-conformance.md` passes;
- two clean environments produce byte-identical artifacts;
- no raw Wasm, WASI, or unknown import crosses the v1 boundary;
- unoptimized parity is complete before any optimization is enabled;
- archive references are absent from release behavior and compatibility claims;
- the forward-compatibility review is recorded with its decisions; and
- the release is labelled 1.0 only after the full-v1 audit is reviewed.

## After v1

Post-v1 work is planned in [Beyond v1](beyond-v1/README.md), which orders the
design tracks into release lines and records their dependencies and designs.
Those documents are direction, not specification: each track still begins with
a specification change, must preserve the v1 static-effect and tooling
contracts or introduce an explicit new version, and is evaluated against user
evidence before it is scheduled. Nothing in them may enter the v1
implementation.

Three tracks were deferred while specifying unions and conversion, each with a
recorded reason rather than an open question:

- **Interface narrowing and runtime type tests.** Narrowing an interface value
  needs a runtime type tag on every such value and contradicts both the
  no-runtime-type-test rule and the erasure rule for `any`. Users who need
  discrimination declare a union instead.
- **Associated types on an interface contract**, and with them a
  per-implementation `try-from` error type. An associated type has one identity
  per implementation, so no atom path addresses it, which conflicts with the
  namespace chapter's rule that every path resolves to at most one entity. It
  would also add a fifth member kind to the flat addressable-member namespace.
  V1 fixes the error to `conversion-error`; a richer error is an ordinary
  `defn`. Generalizing later may require existing `impl` blocks to declare the
  associated type unless the contract supplies a default, which the pre-1.0
  compatibility policy permits when spec, corpus, and roadmap change together.
- **`def` inside a `deftype`** for type-scoped constants. A constant has one
  identity and one atom path, so it fits the member namespace cleanly, but it is
  independent of unions and conversion and nothing in v1 needs it.
