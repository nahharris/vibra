# M4 decision ledger

Step 1's record of the contracts closed before Stage 4A implementation. Each
row has one disposition, its canonical anchors, and one downstream proof
obligation. `new` rows were written into the owning specification chapter in
the Step 1 PR. `settled` rows were already decided by the specification and are
recorded only to fix their proof owner. `recorded` rows are implementation
decisions that are not language rules; their reason lives in the
[README](README.md#fixed-implementation-decisions). `assigned` rows give an
inherited defect an owning step. Stage 4B contracts are Step 13's and are not
in this ledger.

The decisions D1, D2, D3, D5, and D10 were made by the maintainer, Hannah, and
D10 and the dependency versions were revised by her on 2026-10-02 after review. D16 was decided by her on 2026-10-03.
D4 and D6–D15 otherwise were closed with the guide's recommendation and are
reviewed in the Step 1 PR.

## D3.4: the no-cycle premises

Each premise was checked, and the check is repeatable.

| Premise | Where it holds |
| --- | --- |
| Values are immutable and point only to older values | [Value semantics](../../spec/02-type-system.md#value-semantics) states no mutation, references, or shared cells; the interpreter's `RuntimeValue` is a tree built by value from existing operands |
| A module-level `def` cannot reach itself | [Module-value initialization](../../spec/06-runtime.md#module-value-initialization); `reject_global_initializer_cycles` in `vibra-ir`. A capture expression evaluated during an initializer is checked with the initializer as owner, so reading the `def` there is a rejected edge |
| A module function is referenced by index, not by a counted pointer | `Expr::Function` and `CallTarget::Direct` in `vibra-ir` name a function by index |
| A closure holds locals only, so a module value is not held | `resolve_capture` in `vibra-types` builds each capture from an activation or outer-closure slot, never a global. A closure body that names a `def` reads it as `Expr::Global` when it runs, and the static pass deliberately gives the closure body no owner, so `(def f ... (lambda ... (f ...)))` is accepted and creates no counted cycle |
| A `let` binding is visible only from the end of its own pair | [Namespaces and resolution](../../spec/02-type-system.md#namespaces-and-resolution), so a `lambda` in a pair's value cannot capture the name being bound |

No premise was false. The fourth row, that a closure holds no module value,
was not in the plan and is now stated in the runtime chapter.

## D10: the single source for natives and primitives

G7 requires one source for the 19 natives and for primitive rows that have no
Vibra body. Four options were weighed, and Hannah decided on 2026-10-02 to adopt
the host-import option in a Rust-native form, in the style of Bun.

| Option | What it is | Cost |
| --- | --- | --- |
| 1. The Vibra body is the single source | Both backends run the body. The loop-shaped rows, integer and float `to-str` and `parse`, become Vibra bodies, with four `to-bits` and `from-bits` primitive rows for the float ones | Float formatting and parsing in Vibra is slow in Wasm and is real work to write and review. It reclassifies 20 registry rows and adds four. Rejected |
| 2. Two implementations held to shared vectors | The interpreter's Rust and a hand-built Wasm routine per row, with a shared sample table | Float text is written twice and the emitter carries a library of unreviewable Wasm; the backends can drift. Rejected |
| 3. A host import in a Rust-native form (adopted) | The Vibra runtime embeds Wasmtime, and where performance matters the toolchain runs native Rust and escapes from Wasmtime into the host process. Each native and each looping primitive row is Rust in one crate, written against a value-access interface that both backends implement. The interpreter calls it directly; a module imports it from `vibra_native_v1` | A native import is a toolchain-owned dependency of the module, so a module that must run outside the Vibra runtime cannot rely on it, and the toolchain may emit a self-contained body-executing form instead, which M7 decides. The module's linear memory must be readable by the native code, so it is exported under a reserved name for that code alone. Natives are fast, and the single source holds by construction |
| 4. Rust compiled to Wasm and embedded | The same Rust built for `wasm32` and linked into each module | Excluded by the decision (the adopted form is not Rust compiled to Wasm): it needs a `wasm32` target on every CI platform and a build step whose output must be byte-stable, and it gains no speed over native |

Hannah's reason: performance where it matters. The implementation decision, for
the [README](README.md#fixed-implementation-decisions), is that natives live in one
crate, proposed `vibra-native`, written once against a value-access interface, and
that the emitter crate depends only on the import names in `vibra-ir`, not on
that crate. The Vibra body stays the meaning of a native, as the runtime chapter
has always said, and the harness holds native code to it.
